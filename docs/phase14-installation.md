## Final acceptance procedure

From clean committed source, build release images, create a new candidate directory, verify its payload and use the preservation-audited selected upgrade:

```powershell
$deployment = (Get-Content .steward/operator/selection.json | ConvertFrom-Json).directory
node scripts/build-release-images.mjs 0.14.0
node scripts/release.mjs pack --version 0.14.0 --directory "$deployment" --bundle artifacts/releases/steward-0.14.0-rc15 --candidate
node scripts/release.mjs verify --bundle artifacts/releases/steward-0.14.0-rc15
node scripts/upgrade-phase14-selected.mjs "$deployment" artifacts/releases/steward-0.14.0-rc15
node scripts/verify-single-stack.mjs
```

Use a new candidate path if it already exists. Existing signed module versions must not be rebuilt from changed shared code. The module map is `docs/phase14-module-versions.json`. New module packages install separately through the ordinary signed Module Manager; core redeployment does not create financial policy or change module configuration.

The upgrade snapshots every protected record, account, authority and private configuration, then backs up all operational PostgreSQL instances. Only connector health-check revision/time metadata is excluded from connector row comparisons; complete connector payloads and all product/order/financial/mission records remain protected. A failed preservation check requires investigation against the retained private snapshots/backups. No automated destructive database rollback is performed.

Clean installation acceptance uses a new private target and the portable candidate toolkit. It first builds the toolkit, then stops all selected core AND managed-module containers. Cleanup stops every temporary container and restores the original operator even after a failed child:

```powershell
$env:STEWARD_RELEASE_BUNDLE = (Resolve-Path artifacts/releases/steward-0.14.0-rc15).Path
$env:STEWARD_TEST_NETWORK_PREFIX = '10.239'
node scripts/verify-phase14-clean-installation.mjs .steward/phase14-clean-final-02
Remove-Item Env:STEWARD_RELEASE_BUNDLE
Remove-Item Env:STEWARD_TEST_NETWORK_PREFIX
node scripts/verify-single-stack.mjs
```

The network prefix must not overlap retained Docker networks. The runner's presence alone does not establish a successful clean install; inspect the verification archive accompanying the accepted distribution. It preserves stopped archives/volumes and never prunes Docker or erases real operator data. Review the generated report and cleanup errors before proceeding after a failure.

## Additive API routing

After the secured mission routing layer is present, the economic routing provisioner creates an optional `economy` overlay. It adds `/api/v14/` without changing `/api/v2/`, `/api/v13/`, existing origins, credentials or module configuration. It creates no containers, volumes, financial records or policy. It requires an explicit existing deployment directory and never silently chooses a new development stack.

Build and test from the repository root:

```powershell
npm run build -w @steward/installer
npm test -w @steward/installer
node --test scripts/test-compose-operator.mjs
```

The routing-only provisioning command is:

```powershell
$deployment = (Get-Content .steward/operator/selection.json | ConvertFrom-Json).directory
npm run economy:provision -- "$deployment"
```

This command alone does not apply a deployment upgrade. API routing must be applied together with the verified Phase14 core release. Once the complete upgraded configuration has been reviewed by the release installer, the existing `select-deployment.mjs` and Compose helpers recognize `economy/compose.yaml` after mission routing and before image pinning. Ordinary operator commands remain `docker compose up -d`, `docker compose stop`, `docker compose ps` and `docker compose logs` using the same selected project and retained volumes. No second stack is required.

The provisioner records the original runtime identities and source routing hashes. Re-running preserves every generated byte. Identity changes, changed base routes, edited economic overlays, malformed identities and concurrent provisioning fail without overwriting the existing configuration. Review intentional configuration changes explicitly rather than deleting the installed overlay. Temporary staging cleanup is bounded to the newly generated directory.
