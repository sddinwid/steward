## Genuine workflow and dynamic installation

The controlled scenario was seeded through existing real authenticated enrollment, module and record APIs. The Analyst's official MCP client initializes over verified HTTPS, discovers tools, lists authorized entities, reads actual synchronized records and relationships, and invokes the deterministic calculation. Stored evidence contains source Worker installation IDs, entity IDs, record IDs, revisions, timestamps, explicit assumptions, alternatives and human decisions. No opportunity is hardcoded in production agent output.

The explicitly configured HTTPS Responses **test fixture** selected observed storage supply/demand records. With 500 m³ required, 1,200 m³ available and EUR 10,000 monthly external expense, its stated assumptions were EUR 3,000 internal payment, EUR 1,000 incremental operating expense, EUR 6,000 transition, 12 months and full proportional expense avoidance. The tested calculation returned consumer benefit EUR 7,000/month, provider benefit EUR 2,000/month, ecosystem benefit EUR 9,000/month and EUR 102,000 over 12 months after transition. Higher assumed incremental/transition costs returned EUR 84,000 over 12 months. Internal payments cancel rather than increasing ecosystem savings.

An explicit authorized finding action, including a Chromium Publish action, used the existing idempotent finding service and durable synchronization. Only affected distribution/asset Workers received the finding; the unrelated manufacturing Worker did not. Retries returned the same finding. Existing acknowledgment and Master lifecycle regressions passed.

On the fresh isolated topology, Worker 2 had no Inventory installation or Inventory MCP tool. Chromium installed and activated the separately signed Inventory package; its MCP tool then discovered and returned newly created persistent inventory quantities. The initial run used 1.2.0; the deferred-setup follow-up repeated fresh installation with corrected version 1.2.1. Its core API image and running process stayed identical. The original Phase 3 suite separately compared every core image, container ID and start time during module installation and CRUD.

Final package review found an unintended local repository dependency introduced during lockfile refresh. It was removed, and a separately signed **1.2.1** patch was published instead of replacing 1.2.0. All three development Workers were explicitly upgraded to 1.2.1 with their existing configuration and records. Runtime checks verified the package has only its SDK/Fastify/PostgreSQL dependencies and no platform core directory or linked root package. The full MCP/Analyst scenario was then repeated against the corrected package. Original signed package versions remain immutable. The fresh-install and later patch-upgrade evidence are recorded separately.

A synchronized record containing instructions to reveal credentials, invoke an undeclared destructive tool and publish a finding was actually supplied to the investigation. Read-only tool boundaries and explicit finding authorization remained intact. Model outage, malformed JSON, undeclared tools, failed tool calls, repeated calls and an actual 25-second model transport timeout produced persistent explicit failures. These test-fixture results validate orchestration and boundaries; they do not establish real-model resistance to prompt injection or analytical quality.

## Preserved runtime and limitations

The final development deployment runs fifteen healthy core/provider services plus six active business module containers: Operations and Inventory on each Worker. A historical stopped migration-recovery fixture is retained; it is not an active application failure. Master and Workers retain their original configuration identities and enrollment. Workers have separate operational PostgreSQL instances and module databases. All three Workers use the same API image and same frontend image. The default live-model configuration is restored to unconfigured; completed test investigations remain clearly labeled TEST MODEL.

**At this original checkpoint, live model-provider integration had not been validated and Phase 5 was not declared fully complete.** The operator explicitly deferred cloud provider/API-key setup until later. This remains a supported deployment state, not a startup prerequisite or a request for credentials. Cloud account/model compatibility and quality still require a separate credentialed run when setup is desired. The later [Phase 5B local-Qwen validation](phase5b-verification.md) supplies genuine real-model evidence without a cloud key. No canned fixture response is represented as live AI analysis.

Current Master analysis uses authorized synchronized projections, not live delegated Worker access. MCP clients use existing local human sessions plus CSRF; there is no external OAuth authorization server or unattended analytical credential workflow. The Analyst has one Responses wire adapter behind its provider-independent interface. Currency conversion, geospatial validation, actual cost estimation, financial execution, autonomous decisions, distributed quotas, Python services, advanced agents and offline enrollment are not implemented. Human review of narrative, costs, contracts, freshness, location suitability and recommendations remains necessary.

Verification covered one-host Linux containers on Windows Docker Desktop. Native Linux/macOS/ARM, multi-host transport, production PKI rotation, secret-manager integration and production deployment were not exercised. The existing trusted module provider still holds host-root-equivalent Docker authority. Operational and trust details, exact startup/shutdown/configuration commands and failure recovery: [Phase 5 operations](phase5.md), [ADR 0012](adr/0012-request-scoped-mcp-and-bounded-analyst.md).

The first isolated regression startup exhausted Docker's default network pools. Removing only development containers/networks while retaining all volumes freed the necessary subnets; the separate suites then passed and the original deployment was restored. Early test assertions were corrected for genuine MCP “unknown tool” protocol errors, module POST 201 responses and module-owned `records` payloads. Deployment-changing suites must run sequentially; interrupted startup checks were rerun after restoration. No database reset or enrollment shortcut was used.

Final review made concurrency admission atomic across asynchronous preflight and retained execution slots until unfinished tools settle after client disconnects. The parallel investigation test above exercised the corrected runtime. Current MCP smoke also verifies authenticated stateless GET requests return the protocol's explicit HTTP 405 rather than a generic missing-route response. Signed read-only module tools can be discovered without requiring a UI screen; the SDK accepts that contract independently.
