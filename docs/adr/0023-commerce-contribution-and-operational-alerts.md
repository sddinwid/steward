# ADR 0023 — Commerce contribution evidence and operational alerts

Status: accepted for Phase 10A implementation; deployment acceptance is recorded separately.

Sales retains authority over local order financial assessments in its dedicated database. An assessment records explicit production, shipping, transaction and channel cost amounts, their known/estimated basis and an operator evidence reference. Empty amounts mean unknown, including fees. Source order facts cannot be edited through assessments. The separate `cee.sales.finance` permission governs mutations. Approved commerce replication carries only the closed financial evidence schema; customer and delivery data remain private.

Commerce Kit 1.1 supplies the same exact integer calculation to module reports and Master analytics. Gross merchandise sales less source discounts gives booked revenue. Completed quantities determine recognized revenue. Contribution subtracts source refunds and all four cost components. Unknown components or partially recognized orders prevent a complete contribution margin. Estimates remain estimates. This is not net profit: tax, shipping income, overhead and income taxes are excluded. Costs/refunds on multi-SKU orders are not arbitrarily allocated. Currency groups are never converted or combined. Period reports use source order creation time, inclusive start and exclusive end; the retained fulfilled-revenue report keeps its previous completion-time semantics.

Worker screens and forms continue to come from signed module manifests. The generic renderer gains response-driven report summaries and period controls; Worker core does not import Sales or connector screens. Report rows are paginated and product summaries declare their bounds. Master retains its previous gross-margin calculation and adds explicitly distinct contribution evidence, preserving earlier MCP contracts and regression expectations.

Connector conditions are module-owned observations published through an optional, privacy-limited `commerce_exceptions` replication stream. Publication defaults off. Master monitoring additionally requires a per-entity policy approved by a currently enabled registry administrator. Deterministic conditions create existing analytical findings and use existing signed durable delivery, acknowledgment and resolution. Models gain no mutation or manufacturing authority.

Alert deduplication uses installation, module, stream, record and condition code. Source revisions and polling timestamps are not alert identity. An active episode produces one finding; disappearance marks the condition inactive without closing a human-reviewed finding. Reappearance starts a new episode. Advisory transaction locks serialize concurrent ingestion. Disabling a policy or its approving account prevents new alerts. Existing evidence and findings remain retained.

Connector secret format v2 supports up to ten explicitly named stores in one private file. Legacy single-store files normalize to `default` and retain their original source IDs. Other stores namespace remote IDs and webhook receipts. Original remote IDs remain in module-owned records for API reconciliation; authorized local module reads can expose those identifiers. Auxiliary remote-ID fields are excluded from the strict SSMA order contract and Master commerce projection. Production lines must resolve to one connection, and jobs retain that connection. Store identity is pinned before polling; changing an existing connection's store is rejected rather than transferring obligations. Credential rotation preserves identity. Removing a connection never authorizes resubmission or substitution.

All commercial acceptance uses explicit simulators. Simulated results do not establish live Shopify or Printify compatibility. Live credentials, delivery grants, costs, provider scopes, webhooks and financial settlement still require operator validation before commercial use.
