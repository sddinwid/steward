# ADR 0010: Transactional capture and one durable synchronization transport

Status: accepted for Phase 4.

Operational authority stays in each independent module database. A signed module manifest may declare replication v1 projections: table, immutable record ID, monotonic revision and explicitly exported columns. The trusted per-Worker provider installs a shared SDK PostgreSQL outbox and triggers, plus a current snapshot for existing rows, after successful module migrations. Trigger execution and record mutation share the source transaction. No gateway response or cross-database write is used as proof that a record event was persisted.

The Worker uses one transport abstraction for all projected modules and core finding status changes. Core finding updates use the same outbox schema in their own transaction/database. Module outboxes are read/acknowledged through the existing identity-signed TLS provider channel. They are never copied into a second operational queue. This avoids pretending that a transaction can span module/core databases. Source events remain until Master acknowledgment is durable; a crash between remote commit and local acknowledgment causes safe redelivery.

The HTTPS exchange reuses enrolled Worker keys, Master trust profiles and verified TLS. Proofs bind protocol, installation, enrolled entity, timestamp, nonce, events and acknowledgments. Nonces and inbox digests are PostgreSQL-backed. Master signs receipts bound to the request nonce and destination. Event IDs are immutable; changed contents for the same ID conflict. Projections apply only higher per-record revisions; older events remain provenance but cannot overwrite newer data. Equal revision with different contents conflicts. Cross-record global ordering is deliberately unnecessary for these independent upserts.

Remote DNS resolution must also preserve local independence. Node's default getaddrinfo lookup shares libuv threads with local database connection work; repeated resolution of an unavailable Master can starve new PostgreSQL connections despite a live local database. Outgoing Master/provider requests therefore use bounded asynchronous A/AAAA resolution, respect literal addresses and cached hosts-file entries, and have absolute request deadlines in addition to socket timeouts. This boundary was added after the outage regression exposed the contention; changing health assertions or extending timeouts would not fix the dependency.

Pool clients held across asynchronous transport calls also need connection-error listeners while checked out. A local PostgreSQL shutdown must reject queries and fail readiness without turning an unhandled client error into process termination. Core attaches those listeners when connections are established; liveness remains independent of database availability.

Persist attempts, next retry, acknowledgments, last success and errors. Use bounded batches by count and bytes, exponential retry backoff, per-Worker process/advisory exclusion, and persistent module polling fairness. Finding receipt acknowledgments also have durable pending state; no fixed-size recent-event window is treated as an acknowledgment ledger. Outboxes/inboxes are retained without automatic destructive compaction. Poison/conflicting events remain visible for operator review; they are not silently discarded.

Inventory 1.1 adds availability with an additive migration and replication declaration. A local administrator explicitly upgrades its separately signed image; the manager stops its old service, applies migrations and snapshot capture, and requires activation. Existing database/secrets/records persist. This is a controlled forward upgrade with a brief local module outage, not rolling upgrade or automatic rollback. Recovery retains data and uses a corrected compatible package. Core and other Workers remain independently available.
