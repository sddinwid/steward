# ADR 0005 — Pinned Master trust and proof-bound enrollment

Status: accepted. Date: 2026-10-22. Extends ADRs 0001–0004 for Phase 2.

Workers retain their immutable Phase 1 installation ID, role, local entity identity, and operational database binding. Enrollment adds a separate legal-entity relationship and signed certificate in `local_enrollment`; it never rewrites configuration v1 or adopts another database. A Worker installation has a unique Ed25519 key pair generated once by the operator's additive security provisioner. The private key is a read-only per-installation secret mount, never a browser credential or image asset. Master binds both installation ID and public key uniquely.

A Worker can select only operator-installed Master trust profiles. Each profile pins an HTTPS backchannel URL, browser origin, issuing Master installation ID, Ed25519 signing public key, and TLS CA. Redirects are not followed. Every connection validates the TLS chain/hostname, then verifies Master ID and signing-key pins. The web wizard cannot substitute an arbitrary URL or install trust from a server's self-assertion. Initial trust delivery is an operator responsibility over an authenticated channel; the development provisioner establishes this boundary locally. No trust-on-first-use shortcut exists.

The browser authorization interaction is inspired by the separation in [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628), but is a Steward-specific proof-of-key protocol, not an implementation of OAuth/OIDC. The local Worker administrator initiates enrollment. Master returns a random public user code to locate the request. The user signs in only at Master's distinct HTTPS origin, checks installation ID/key fingerprint, chooses an existing eligible entity within their explicit scope, submits the request, then a scoped administrator approves or rejects it. A registry administrator has no implicit enrollment scope. Phase 2 permits the requester to approve their own request; mandatory dual control is not implemented.

Backchannel operations contain a canonical, domain-separated Ed25519 signature over protocol, operation, installation ID, public key, stable request ID, random nonce, timestamp, and operation data. Proof timestamps have a 60-second acceptance window; durable nonces remain five minutes, longer than the acceptance window including allowed future timestamps. Installation and request row locks, uniqueness constraints, and transactions make fresh signed retries idempotent while rejecting exact replay and key/installation substitution.

Approval creates a signed format-v1 grant bound to issuer, audience, entity, request, Worker key thumbprint, grant ID, capability, and a maximum ten-minute validity interval. Redemption checks current account enablement, both authorizing administrators' entity scopes, entity eligibility, and exact grant binding before writing one enrollment certificate and its audit event atomically. An identical business retry returns the same persisted certificate. Lost responses can be recovered through fresh signed polling, including after the original grant expires once enrollment is complete.

Grants and certificates are proof-bound assertions, not bearer login credentials. They travel only over the authenticated server-to-server channel; administrative and local browser APIs omit them. Private keys and Master passwords never travel to Workers. Versioned grant contracts preserve a future offline-transport extension point, but there is no offline enrollment workflow in Phase 2.
