# 0022 — Evidence-derived business intelligence with a generic module renderer

Status: accepted for v0.9.1 implementation; release acceptance is recorded separately.

The verified v0.9.0 release remains tagged at `66481a9`. v0.9.1 refines presentation without changing module authority, installation contracts, event routing or analytical execution.

Investigation catalog metadata is derived from retained results on read. Titles, categories, affected companies, source counts and conditional impacts do not require a running model. No historical prompt, result, reference or calculation is rewritten. Catalog pagination and detail reads enforce account ownership and current entity scope. Long questions remain in detail rather than becoming list titles.

Executive priorities are deterministic: open review first, explicit severity (critical, warning, informational, unknown), newest creation time, then stable finding identity. No inferred urgency, confidence percentage or cross-currency monetary ranking is introduced. Projected resource-sharing benefits come only from the existing deterministic calculation. Publication and acknowledgment never imply business approval or execution.

Financial reporting reuses the existing commerce calculation service over approved source projections. Each entity/currency group selects its most recent 20 observations, matching the bounded analytical contract. The report explicitly states its selection and observation range; it is not a complete-period financial statement. Costs retain known/estimated/incomplete basis, unknowns remain unknown, and gross margin is not net profit. References preserve entity, module, stream, ID and revision.

Provider status is separate from stored intelligence. A bounded TLS GET probes only the deployment-managed endpoint, without generating a model response. Endpoint reachability does not certify model readiness. No endpoint or credential is supplied by browser input. Provider configuration remains operator-managed in private deployment files; authorized administration explains that path rather than collecting secrets in the frontend.

Worker navigation is still generated from verified, permission-filtered installed manifests. Collapse state is per browser origin/account and stores category names only. Screen/API identities remain unchanged. Shared rendering supplies field spacing, currency conversion for display/input only, dates, statuses, action confirmation, search and existing API pagination. No Inventory, Sales, Shopify, Printify or other module screen is compiled into core. The module registry, resolver and workflow permissions remain authoritative.

No schema migration is required. Regression testing exposed existing Inventory/Sales/Printify dependencies on the monorepo root. Independently signed patch packages Inventory 1.4.2, Sales 1.1.3 and Printify 1.0.6 remove those declarations without changing operational code or migrations. Publication now rejects direct core dependencies. Run lockfile updates from the module directory: npm install with a different --prefix can treat the current root as an implicit package and reintroduce the defect. Superseded diagnostic patch descriptors remain retained but are excluded from the 0.9.1 distribution. Historical release images and catalogs are not overwritten.
