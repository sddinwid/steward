## Gaps established before shared implementation

The existing signed module/SDK/business-kit, dedicated databases, module-contributed UI, transactional inbox/outbox, local SSMA registry/resolver/bindings/obligations and Master synchronization are the foundations. Do not replace them. Generic business resources currently filter only kind/status/query, read all record fields and audit mutations only. They have no program membership/case assignment checks, and cached action receipts can bypass subsequently revoked relationships. Worker-local administrator API permission does not constitute participant-record authorization.

Existing SSMA providers/bindings are strictly Worker-local; provider foreign keys reference local module installations and the resolver preserves an entity boundary. Cross-entity service workflows therefore need an explicit certified, TLS-pinned peer extension to that registry and its durable routing, not fabricated local modules, global discovery, removed entity checks, standalone service calls or Master-held case relays. Existing enrollment certificates/private keys can authenticate peer profiles and request/receipt proofs without making Master an availability dependency.

Assets owns facilities, legal ownership/custody/use and maintenance. Housing owns operational units, reservations, occupancy and placements referencing authorized canonical assets. Workforce owns skills/training catalogs, positions, seat accounting and achievements. Pathways owns minimal authorized referrals, review and outcomes; it must not recreate catalogs. These existing modules lack the required signed service-provider capabilities and need additive immutable package versions. Inventory legacy reservation operations are Sales-specific; service supplies require a new governed capability while preserving the legacy contract. Procurement already supports draft replenishment; no new module may auto-create a purchase or funding commitment.

Generic Master analytics currently returns every entity-authorized projection and treats registry administration as broad entity access. Mission aggregates need program/disclosure authorization at all raw API, scientific snapshot/history, MCP, finding/evidence and UI paths, not just a new dashboard. Incoming/outgoing mission events require closed module/stream-bound schemas before persistence. Capture only explicitly reviewed publication rows, never participant tables. Worker MCP summaries must call safe aggregate operations only.

Thresholds alone are insufficient: successive publications, arbitrary filters, totals minus vacancies, prices times counts and shared training/inventory projections can reveal suppressed activity. Legacy Workforce exact availability must not expose mission enrollment changes. Participant-related inventory demand must be bulk/non-identifying. Programme reporting must provide a fixed, sealed, nonoverlapping cohort with one immutable disclosure and complementary whole-vector suppression, including capacity/cost proxies where necessary. No individual identities or arbitrary dimensions reach Master. This is a bounded synthetic MVP privacy design, not differential privacy, HMIS certification or a claim of complete legal compliance.

## Decisions

Four independent signed modules: steward.housing.management, steward.housing.services, steward.employment.pathways and steward.services.food. Commercially neutral configuration and versioned contracts; dedicated operational databases and append-only migrations. Only synthetic participant identities, with per-referral opaque audience/program/purpose-scoped aliases. No names, contact data, assessments, case notes or individual circumstances in general synchronization/MCP. Membership and case-assignment relationships are explicit module-owned records; consequential approvals require specific permission, current relationship, reviewer and timestamp.

Add opt-in reusable business-kit access/filter/audit hooks, preserving all legacy module behavior. Filter before pagination, reauthorize replayed receipts and retain minimal denied/read audit outside failed business transactions. Add signed metadata for safe reference-field lookups to the generic UI renderer where needed; do not hardcode module screens into Worker core. Routine staff use labeled forms/actions, not provider bindings/JSON.

Extend existing SSMA with reviewed peer profiles, verified installed capability metadata, source/destination entity/program/purpose grants, pinned package/provider installation identities, TLS and signed bounded envelopes. Keep local entity-only resolution unchanged; remote resolution requires explicit bilateral grants and a checked destination context. Persist routes/retries and original obligation pins. No distributed database transactions, secret sharing, blind provider substitution or retries after uncertain consequential effects.

Publish only reviewed sealed aggregate releases with fixed schemas and current program disclosure permissions. Suppressed values remain null, not zero. No revision history or repeated narrower views may undo suppression. Mission costs/resources use explicit reporting bases, source provenance and stable allocation/transfer identities. Revenue, contribution, legally distributable resources, approved availability, commitments, transfers, spending and modeled expansion remain distinct; no inferred available funding or intercompany double counting.

Reuse existing scientific capability catalog, bounded Python service, immutable runs, charts, MCP and provider-independent Analyst. Add a bounded integer service-capacity planning method using current SciPy rather than new scientific dependencies. Scientific requests contain only approved aggregate releases; old v1 provenance/digest semantics remain unchanged. AI is advisory and has no case access, eligibility/placement/hiring/transfer authority.
