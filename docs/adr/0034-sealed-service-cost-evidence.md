# ADR 0034: Sealed service evidence and independent financial reporting

Status: source/API, scoped Master reporting, exact-money renderer helpers and migration preservation verified; actual deployment/browser/scientific/MCP release gates pending.

Housing Management 1.0.2, Participant Services 1.0.4, Employment Pathways 1.1.1 and Food Services 1.0.2 add an optional compatible `mission.cost-evidence` / `steward.sealed-programme-cost` 1.0.0 capability. These new packages are unpublished and require platform 0.14.0. Existing operational APIs, case scopes, records and all previously applied migration bytes are retained. New append-only migrations bind cached cost commands to their complete approved original peer context before the ordinary inbox cache can answer.

The provider reads only an existing sealed programme release. Current approved SSMA programme/actor/audience authority and programme management, finance and disclosure rights are required even for cached replies. No participant member table, alias, case narrative or account credential is returned. The existing canonical suppression rules apply independently at source and receiver. The closed response contains fixed cohort metrics, original period/currency and operational cost observations; it explicitly confers no accounting authority and omits historical cash-availability statements.

Mission Budget uses the existing registry/resolver, reviewed programme bindings/workflows, pinned audience and durable private outbox/receipt flow. Immutable source profiles select an original provider/programme/release. Imported evidence is an immutable fact; it neither creates cash nor authorizes spending. A separate local evidence-approval record binds the exact source digest, budget series/category and current policy version. A different current reviewer must satisfy its quorum. Actual expenses still require their own monetary approvals and executor authority. Source periods are half-open intervals, and an expense observation must belong to the fixed source period and target budget. Cross-entity service evidence must name its original intercompany counterparty. Unknown operating costs and suppressed denominators remain unknown.

Budget reporting separates operational cost observations, posted linked financial expenditure, financial classification and recorded service units. Exact ratios retain an integer-cent numerator and recorded-unit denominator; no model arithmetic or arbitrary rounding creates an authoritative amount. Internal/intercompany amounts do not create additional ecosystem value. Reversals retain original journals and change only the net recorded expense calculation. A ratio is a descriptive link to a fixed cohort, not proof of causation, programme completeness, unique people across programmes or individual financial worth.

A budget's financial disclosure cannot authorize re-disclosure of another module's protected service metrics. Its sealed summary carries only its own classified spending and full opaque pointers to the original service evidence. Master resolves service counts and operational costs only after checking the same named account's independent current disclosure for that original programme. Revoking the service disclosure removes those values from comparisons while leaving independently authorized budget spending visible. Suppressed cohorts yield no count, operating cost, unit estimate or cost-per-recorded-unit ratio. Master does not silently consolidate overlapping cohorts or add operational observations to financial journals.

Money entry remains in the shared signed-module renderer. Exact decimal parsing rejects excess precision rather than rounding floating-point values. Optional version-gated currency-reference metadata reads only an authorized local choice's declared ISO currency; an unresolved reference does not fall back to a company display currency. Backend records retain their immutable programme currency. No operational screen is hardcoded into Worker core.

Before publishing any new package, source tests preserve 54 baseline migration hashes. Existing mixed/CRLF byte sequences are authoritative where already published/applied. Printify's old CRLF migrations now have explicit checkout attributes matching their installed signed package, without changing SQL or database state. New Phase 14 migration files and generated hashes use canonical repository LF bytes. This fixes source reproducibility without rewriting applied migrations or previous release tags.
